## 开篇：老项目有什么问题

这个工具最早是一套 Java + XML View 的 Android 工程，用 AIDE 在手机上直接编译。它能用，功能也不缺——USB 通信、FDL 加载、PAC 固件解析、分区表读写、批量刷机、Kickto 监听，核心引擎 `UsbFlashEngine.java` 有 152KB。

但界面层面的问题很明显：

**第一，样式基本靠 drawable 凑。** 每一张卡片、每一个按钮都是一个 XML shape，圆角、渐变、描边全靠 `bg_xxx.xml` 堆出来。想改一处风格要改十几张 drawable，改完还得在 `MainActivity` 里用 `setBackgroundResource()` 一个个设回去。老代码里那段 `int[] btnIds = { btnConnect, btnReadPart, ... }` 然后循环 `setBackgroundResource` 的写法，就是这么来的。

**第二，界面和业务逻辑全绑在一起。** 一个 `MainActivity.java` 113KB，`findViewById` 拿到几十个控件，`runCmd()` 里一大串 `if/else` 分派，引擎回调直接在 Activity 里改 TextView。

**第三，做不了复杂动效。** XML View 做"按下跟手扩散的光晕""拖动时速度拉伸"这类效果，成本极高，几乎全靠自定义 View 手写。

所以我决定重写 UI。而且目标很明确：**做成 iOS 26 那种液态玻璃的质感**，不是简单的半透明磨砂。

这里有一个现实约束：`AndroidLiquidGlass`（Kyant0）从 2.0.0 起已经改成 **Compose Multiplatform 库**了，官方 release 说明写得很直白：

> *"Backdrop becomes a Compose Multiplatform library now! Remove Android related effects, use Compose version instead"*

也就是说它**没有 View 版 API**。想在旧工程里 `implementation` 然后直接调用，是不可能的。这直接把重写方向钉死了：必须上 Compose。

## 第一章：液态玻璃的技术原理

这一章是全文最核心的部分。很多人以为"液态玻璃"就是「半透明白底 + 高斯模糊 + 一圈高光」，那是最初级的版本。真正的液态玻璃要做到三件事：**背景真实模糊、边缘真实折射、边缘有色散**。下面拆开讲。

### 1.1 Backdrop 录制机制

Compose 里画东西最终都走 `GraphicsLayer`。这个库的做法是：把某一层 UI 的内容**单独录制成一张 GPU 纹理**，之后所有玻璃组件都从这张纹理上采样，而不是从屏幕缓冲上采样。

代码只有两行：

```kotlin
// 1. 创建一个"背景图层"句柄
val backdrop = rememberLayerBackdrop()

// 2. 把壁纸层挂上去，这一层的内容会被录成纹理
Box(
    Modifier
        .fillMaxSize()
        .layerBackdrop(backdrop)
) {
    WallpaperBackground(blurRadius = 6f, dim = Color(0x140B1220))
}
```

```
┌──────────────────────────────────────┐
│  Box + Modifier.layerBackdrop(...)   │  ← 被录制
│  ┌────────────────────────────────┐  │
│  │ 壁纸 JPG + RenderEffect 模糊   │  │
│  │ + 压暗层 + 上下渐变            │  │
│  └────────────────────────────────┘  │
└──────────────────────────────────────┘
              │
              │  录制成 GPU 纹理
              ▼
      ╔═════════════════╗
      ║  Backdrop 纹理  ║  ← 之后所有玻璃都采它
      ╚═════════════════╝
        │      │      │
        ▼      ▼      ▼
   玻璃卡  玻璃按钮  底部玻璃导航
```

关键点：**这一层可以是任意内容**，不一定是静态图片。你放个视频、放个渐变、放个滚动列表进去，玻璃就会折射那里的实时内容。这也解释了为什么"背景越花哨，玻璃效果越明显"——如果背景是纯白，玻璃折射出什么都是白，看着就像一块脏了的塑料板。所以专门给壁纸加了压暗层和上下渐变，就是为了让玻璃的折射和高光能"看见"。

### 1.2 AGSL 着色器折射

真正干活的是 `RuntimeShader`（AGSL，Android 13 / SDK 33+ 才有的 API）。它是一个片元着色器：**屏幕上每一个属于玻璃的像素，都要跑一遍这段程序**。

伪代码大致长这样：

```glsl
// 片元着色器：输入当前像素坐标，输出该像素颜色
uniform shader backdropTex;   // 前面录制好的背景纹理
uniform float2 size;          // 玻璃面板尺寸
uniform float  cornerRadius;  // 圆角半径
uniform float  refractHeight; // 折射影响范围（边缘多宽开始弯）
uniform float  refractAmount; // 折射强度（最大偏移像素数）
uniform float2 lightDir;      // 光源方向

// ---- ① SDF：有符号距离场 ----
// 返回负数=在玻璃内，绝对值=到边缘的距离
float roundedRectSDF(float2 p, float2 halfSize, float r) {
    float2 d = abs(p) - halfSize + r;
    return length(max(d, 0.0))
         + min(max(d.x, d.y), 0.0)
         - r;
}

// ---- ② 法线：SDF 的梯度 ----
float2 sdfGradient(float2 p) {
    float e = 0.5;
    return normalize(float2(
        roundedRectSDF(p + float2(e,0), ...) - roundedRectSDF(p - float2(e,0), ...),
        roundedRectSDF(p + float2(0,e), ...) - roundedRectSDF(p - float2(0,e), ...)
    ));
}

half4 main(float2 p) {
    float d = roundedRectSDF(p, size * 0.5, cornerRadius);

    // 玻璃外，直接丢弃
    if (d > 0.0) discard;

    // ---- ③ 边缘权重：越靠边，折射越强 ----
    float edge = 1.0 - smoothstep(0.0, refractHeight, -d);

    // ---- ④ 法线推导 ----
    float2 n = sdfGradient(p);

    // ---- ⑤ 折射采样（按法线方向偏移） ----
    float2 offset = n * refractAmount * edge;
    half4 refracted = backdropTex.eval(p + offset);

    // ---- ⑥ 色散：R/G/B 用不同折射率 ----
    half r = backdropTex.eval(p + offset * 1.03).r;
    half g = refracted.g;
    half b = backdropTex.eval(p + offset * 0.97).b;
    half4 col = half4(r, g, b, 1.0);

    // ---- ⑦ Fresnel 高光：法线与光源夹角 ----
    float fresnel = pow(1.0 - abs(dot(n, lightDir)), 3.0);
    col.rgb += fresnel * edge * 0.35;

    return col;
}
```

拆开看每一步在解决什么问题：

**SDF（有符号距离场）** 是这个技术的最大技巧点。传统做法要判断"这个像素在不在圆角矩形内、离边多远"，得写好几个 `if` 判断。SDF 把"距离"变成一个连续函数：内部是负数、外部是正数、零值正好是边界。有了连续距离，后面所有"边缘处效果更强"的插值都只需要一个 `smoothstep`，不用写分支，GPU 也不会因为分支跳转卡住。

**法线推导** 是"透镜感"的来源。真实玻璃是有厚度的，边缘因为曲率大，法线是倾斜的；中心的法线是垂直的。SDF 的梯度恰好就是法线方向（因为 SDF 沿边界方向变化率为 0，法线方向变化率最大）。拿梯度当法线，就等于给玻璃面板自动算出了一个"凸透镜"的几何形状。

**折射采样** 就是拿这个法线去偏移纹理坐标。偏移量在中心是 0（法线垂直，眼睛看到的就是正后方），在边缘最大（法线倾斜，光被"掰弯"了）。所以玻璃中心清晰、边缘蜿蜒——这就是液态玻璃"厚度感"的本质。

**色散** 是最后那块彩虹边。真实光学中不同波长折射率不同，红色偏折最小、紫色最大。这里用三个不同系数采样 R/G/B 三个通道再拼起来，边缘自然出现彩边。这个效果很吃参数，**过强会让文字发虚**，刷机工具的日志里全是十六进制地址，所以这里调得偏保守。

**高光** 是法线与光源方向的点积，加一个 `pow` 控制衰减，模拟 Fresnel 反射——掠射角大的地方更亮。

这套东西在 Compose 里其实不用自己写，库的 `lens()` 就是干这个的：

```kotlin
effects = {
    blur(blurRadius.toPx())
    lens(
        refractionHeight = 16.dp.toPx(),
        refractionAmount = 18.dp.toPx(),
        depthEffect = false,          // 是否模拟面板厚度
        chromaticAberration = true    // 开/关色散
    )
}
```

`refractionHeight` 控制"边缘多宽开始弯折"，`refractionAmount` 控制"偏移强度"。`GlassSurface.kt` 把这两个都开成了构造参数，不同层级的玻璃给不同值：

```kotlin
@Composable
fun GlassSurface(
    backdrop: Backdrop,
    modifier: Modifier = Modifier,
    shape: Shape = RoundedCornerShape(24.dp),
    blurRadius: Dp = 12.dp,
    refractionHeight: Dp = 16.dp,
    refractionAmount: Dp = 18.dp,
    chromaticAberration: Boolean = true,
    highlightAngle: Float = 45f,
    highlightAlpha: Float = 1f,
    ...
) {
    Box(
        modifier = modifier.drawBackdrop(
            backdrop = backdrop,
            shape = { shape },
            effects = {
                blur(blurRadius.toPx())
                lens(
                    refractionHeight = refractionHeight.toPx(),
                    refractionAmount = refractionAmount.toPx(),
                    chromaticAberration = chromaticAberration
                )
            },
            highlight = { Highlight(style = HighlightStyle.Default(angle = highlightAngle)) },
            shadow = { Shadow.Default },
            innerShadow = if (showInnerShadow) { { InnerShadow.Default } } else null
        )
    )
}
```

调参规律总结成这样一张表：

| 想要的效果 | 调哪个参数 |
|---|---|
| 玻璃更"厚"、透镜感更强 | 调大 `refractionAmount` |
| 边缘弯折范围更宽（整块都在扭） | 调大 `refractionHeight` |
| 彩虹边更明显 | 开 `chromaticAberration` / 提高色散系数 |
| 更磨砂、更"奶" | 调大 `blurRadius` |
| 更像"贴在玻璃上的纸" | 加 `onDrawSurface` 画一层半透明色 |

### 1.3 能力分级降级

`RuntimeShader` 是 API 33 才有的。minSdk 是 23，所以必须分级：

```
┌──────────────────┬──────────────────────────────────────────┐
│ Android 13+      │ RuntimeShader（AGSL）真折射 + 色散        │
│ SDK 33 及以上    │ 完整液态玻璃                              │
├──────────────────┼──────────────────────────────────────────┤
│ Android 12       │ 只能用 RenderEffect.createBlurEffect      │
│ SDK 31 ~ 32      │ 真模糊，但没有折射和色散                  │
├──────────────────┼──────────────────────────────────────────┤
│ Android 6 ~ 11   │ 半透明 + 渐变 + 描边 + 高光               │
│ SDK 23 ~ 30      │ 磨砂玻璃质感（外观接近，没有光学效果）    │
└──────────────────┴──────────────────────────────────────────┘
```

这三档不是我发明的，是硬件和系统 API 的客观边界。要说清楚的是：**低版本不会"崩"，只是不好看**。所有高版本 API 调用都在 `Build.VERSION.SDK_INT` 判断之内，老系统上根本不会加载到那些类，不会触发 `NoClassDefFoundError`。

做法是让库自己探测：能力够就走 AGSL，不够就走退化路径。业务代码完全不用管，`GlassSurface(...)` 的调用代码在三档系统上一模一样，变的只是最终绘制出来的东西。

### 1.4 自采样问题

这是踩过的第一个理论坑，值得单独说。

`layerBackdrop(backdrop)` 会把**这一层 Box 里的所有内容**录进纹理。如果把玻璃组件也放在这个 Box 里面，就会出问题：

```
玻璃要采样 backdrop，
但 backdrop 这一层正在录制玻璃，
录制玻璃又需要采样 backdrop……
```

结果就是递归——轻则画面错乱，重则直接崩。这个问题在任何"采集背景 → 渲染前景 → 前景并入背景"的管线里都存在。

官方库的处理方式很优雅：**背景层单独一个 Box，玻璃层不在录制范围内**。

```kotlin
Box(Modifier.fillMaxSize()) {

    // 只有这一层被录制，里面只有壁纸
    Box(
        Modifier
            .fillMaxSize()
            .layerBackdrop(backdrop)
    ) {
        WallpaperBackground(blurRadius = 6f, dim = Color(0x140B1220))
    }

    // 玻璃层在录制范围之外，采样 backdrop 不会采到自己
    Column(Modifier.fillMaxSize()) {
        GlassSurface(backdrop = backdrop, ...) { /* 顶栏 */ }
        GlassSurface(backdrop = backdrop, ...) { /* 进度条 */ }
        // ……
    }
}
```

这个结构看起来理所当然，但一开始就是把它写错过的——把玻璃和壁纸放在同一个被录制的 Box 里，然后困惑为什么画面会自己套自己。

## 第二章：从官方 Catalog 到实际移植

官方的 Catalog 是一个完整的示例 App，要做的是把组件抠出来塞进自己的项目。

### 2.1 移植清单

从官方 Catalog 移植过来的文件放在 `ui/compose/catalog/`：

```
ui/compose/catalog/
├── LiquidBottomTab.kt        1.8KB   单个 Tab
├── LiquidBottomTabs.kt      12.4KB   底部导航（最复杂的组件）
├── LiquidButton.kt           4.7KB   胶囊按钮
├── LiquidSlider.kt           8.7KB   进度滑块
├── DampedDragAnimation.kt    6.4KB   阻尼拖拽动画
└── InteractiveHighlight.kt   5.1KB   交互高光
```

移植原则只有一条：**参数一个都不改**。比如 `LiquidButton` 官方的效果链就是 `vibrancy() + blur(2dp) + lens(12dp, 24dp)`，高度 48dp，胶囊形状——原样照搬，一个字都不动。这样视觉上才能和官方 Catalog 完全一致。

改动的地方只有两类：

**第一，包名和 import 改成 `com.kyant.shapes.Capsule`。** 官方的 `Capsule()` 形状来自 `io.github.kyant0:shapes:1.2.1`，所以这个依赖必须单独引入——官方 POM 里本来就带，但显式声明更稳妥。

**第二，对外暴露的参数收敛。** 官方组件往往是"什么都能传"，移植版里只保留项目真正用得到的口子。

### 2.2 底栏的"四层"结构

底部导航是整个项目里最复杂的组件，官方用了 4 层叠在一起。第一次看源码的时候觉得"这也太夸张了"，直到试着简化它，才发现每一层都有用。

```
┌───────────────────────────────────────────────┐
│ ① 底层玻璃底栏                                 │
│    drawBackdrop: vibrancy + blur(8dp)         │
│                  + lens(24dp, 24dp)           │
│    height 64dp, Capsule                       │
├───────────────────────────────────────────────┤
│ ② 上半层：按下的蓝色着色层（alpha = 0 的幽灵层）│
│    layerBackdrop(tabsBackdrop) → 被录成纹理    │
│    colorFilter = tint(accentColor)            │
│    lens 强度 = 24dp * pressProgress           │
├───────────────────────────────────────────────┤
│ ③ 滑块（真正在动的那个）                        │
│    backdrop = rememberCombinedBackdrop(       │
│                   backdrop, tabsBackdrop)      │
│    lens(10dp*p, 14dp*p, chromaticAberration)  │
│    + Highlight + Shadow + InnerShadow         │
├───────────────────────────────────────────────┤
│ ④ 文字（content）                              │
└───────────────────────────────────────────────┘
```

关键在第 ② 层和第 ③ 层的配合：

**第 ② 层是一个 `alpha(0f)` 的"幽灵层"** ——它不可见，但只要挂了 `layerBackdrop(tabsBackdrop)`，它的内容（也就是被 `tint(accentColor)` 染成蓝色的那排文字）就会被录制成一张独立纹理。

**第 ③ 层的滑块同时采样两个源**：`rememberCombinedBackdrop(backdrop, tabsBackdrop)`。也就是说，滑块既能看到后面的壁纸，也能看到"蓝色文字"那张纹理。

结果就是：滑块扫过某个 Tab 的时候，会把那个 Tab 的蓝字"折射"进自己体内，而且因为开了色散，边缘还有彩虹光。这才是"液态玻璃滑块"该有的样子——它不是在文字下面滑一块半透明板，它是**真的把那块区域当成了光学介质**。

官方源码里这段大概是这样：

```kotlin
// ② 幽灵层
Row(
    Modifier
        .clearAndSetSemantics { }
        .alpha(0f)
        .layerBackdrop(tabsBackdrop)              // 录成独立纹理
        .drawBackdrop(
            backdrop = backdrop,
            shape = { Capsule() },
            effects = {
                val p = dampedDragAnimation.pressProgress
                vibrancy()
                blur(8.dp.toPx())
                lens(24.dp.toPx() * p, 24.dp.toPx() * p)
            },
            onDrawSurface = { drawRect(containerColor) }
        )
        .height(56.dp)
        .graphicsLayer(colorFilter = ColorFilter.tint(accentColor))
)

// ③ 滑块
Box(
    Modifier
        .drawBackdrop(
            backdrop = rememberCombinedBackdrop(backdrop, tabsBackdrop),
            shape = { Capsule() },
            effects = {
                val p = dampedDragAnimation.pressProgress
                lens(
                    10.dp.toPx() * p,
                    14.dp.toPx() * p,
                    chromaticAberration = true
                )
            },
            highlight = { Highlight.Default.copy(alpha = p) },
            shadow = { Shadow(alpha = p) },
            innerShadow = { InnerShadow(radius = 8.dp * p, alpha = p) },
            layerBlock = {
                // 速度拉伸：滑块被"甩"的时候横向拉长、纵向压扁
                val velocity = dampedDragAnimation.velocity / 10f
                scaleX /= 1f - (velocity * 0.75f).coerceIn(-0.2f, 0.2f)
                scaleY *= 1f - (velocity * 0.25f).coerceIn(-0.2f, 0.2f)
            }
        )
        .height(56.dp)
        .fillMaxWidth(1f / tabsCount)
)
```

注意 `layerBlock` 里那段速度拉伸：`scaleX` 会随速度反比缩小分母，于是滑块被甩出去时横向变长、纵向变扁。这是个很细的手感，但加上之后整个拖动就"活"了。

### 2.3 把官方的 DampedDragAnimation 拆成 5 个 Animatable

官方手感好的原因，是读了 `DampedDragAnimation.kt` 才明白的。

原先自己写拖拽用的是 `dampingRatio = 0.32` 的欠阻尼弹簧，也就是**会来回弹几下**。看起来"活泼"，但每次切 Tab 都晃三下，越用越烦。

官方用的是：

```kotlin
private val valueAnimationSpec = spring(1f, 1000f, visibilityThreshold)
private val velocityAnimationSpec = spring(0.5f, 300f, visibilityThreshold * 10f)
private val pressProgressAnimationSpec = spring(1f, 1000f, 0.001f)
private val scaleXAnimationSpec = spring(0.6f, 250f, 0.001f)
private val scaleYAnimationSpec = spring(0.7f, 250f, 0.001f)
```

`dampingRatio = 1.0` 意味着**过阻尼**——完全不回弹，只做平滑追踪。追到目标就停，干净利落。

更关键的是它把状态拆成了 5 个独立的 `Animatable`：

```
Animatable: value          ← 位置，过阻尼
Animatable: velocity       ← 速度，欠阻尼（这就是"甩"的感觉来源）
Animatable: pressProgress  ← 按压进度，过阻尼
Animatable: scaleX         ← 横向缩放
Animatable: scaleY         ← 纵向缩放
```

为什么要拆？因为**手指是多维的**。手指按下、拖动、松开，这三个动作在时间上是重叠的：按下时 pressProgress 在涨，拖的时候 value 在跟，松手瞬间 velocity 还在，scale 还在弹。如果用一条动画曲线同时表达这些，一定会互相打架——拖的时候会打断按下的动画，松手时会打断拖动的动画。

拆开之后每个维度各有各的弹簧、各有各的时钟，互不影响。这就是"多手势不打架"的原理。

这段原样搬进了 `catalog/DampedDragAnimation.kt`，并在注释里记下了这个对比：

```kotlin
/**
 * 为什么官方的滑动"稳"：
 * dampingRatio = 1.0 表示过阻尼，完全没有回弹，只做平滑追踪。
 * 之前用 0.32 是欠阻尼，会来回弹几下，所以手感完全不同。
 * 另外它把位置/速度/按压进度/缩放拆成 5 个独立 Animatable，
 * 各自有独立的弹簧参数，互不干扰 —— 这才是多手势不打架的原因。
 */
```

Tab 切换后滑块落位用的也是过阻尼：

```kotlin
onDragStopped = {
    val targetIndex = targetValue.toInt().coerceIn(0, tabsCount - 1)
    currentIndex = targetIndex
    animateToValue(targetIndex.toFloat())
    animationScope.launch {
        offsetAnimation.animateTo(0f, spring(1f, 300f, 0.5f))
    }
}
```

### 2.4 GlassButton：官方 API 加本地角色

官方的 `LiquidButton` 只接受 `tint` 和 `surfaceColor` 两个颜色参数。项目需要区分"主按钮、成功、危险、警告、次要"五种语义角色，而且页面里已经有几十处 `GlassButton(backdrop, "文本", { ... })` 的调用。

所以在官方组件外面包了一层 `GlassButton`，**保持调用签名不变**，内部映射到官方参数：

```kotlin
enum class GlassRole(val tint: Color, val textColor: Color) {
    Primary(Color(0xFF4F7CFF), Color.White),
    Success(Color(0xFF22C55E), Color.White),
    Danger(Color(0xFFEF4444), Color.White),
    Warning(Color(0xFFD97706), Color.White),
    Secondary(Color(0x30FFFFFF), Color(0xFF0B1220))
}
```

上色用的是官方同款技巧：先 `BlendMode.Hue` 染一遍色，再叠一层 75% 透明的同色。为什么要两层？因为 `Hue` 混合模式只改色相、保留底下的明度，如果只染一次，颜色会被背景亮度带偏；再叠一层半透明纯色就能把明度也拽回来。官方 `LiquidButton` 用的就是这个组合，直接沿用了。

### 2.5 刷新率适配

移植过程中还发现一个官方没管的问题：**动画参数是按照某个刷新率调的，换设备手感就变。**

60Hz 每帧 16.7ms，120Hz 每帧 8.3ms，144Hz 每帧 6.9ms。同样一段 90ms 的按压补间，在高刷屏上跑出来的帧数少一半，视觉上会显得"闪"而不是"压"。

所以写了 `DeviceRefreshRate.kt`，按刷新率分组给不同的时长和弹簧：

```kotlin
fun scaleDuration(base60Ms: Int): Int {
    return when {
        hz >= 144 -> (base60Ms * 0.78f).roundToInt()
        hz >= 120 -> (base60Ms * 0.84f).roundToInt()
        hz >= 90  -> (base60Ms * 0.92f).roundToInt()
        else      -> base60Ms
    }
}

fun pressSpring(): SpringSpec<Float> {
    return when {
        hz >= 144 -> SpringSpec(dampingRatio = 0.52f, stiffness = 420f)
        hz >= 120 -> SpringSpec(dampingRatio = 0.48f, stiffness = 470f)
        hz >= 90  -> SpringSpec(dampingRatio = 0.42f, stiffness = 540f)
        else      -> SpringSpec(dampingRatio = 0.32f, stiffness = 620f)
    }
}
```

高刷屏上刚度降、阻尼提高，让观感和 60Hz 一致。检测刷新率还有个坑：`Display.mode.refreshRate` 返回的可能是 `59.94` / `119.88` 这种非整数（PAL 制式的历史遗留），所以要做归一化：

```kotlin
fun normalizeHz(raw: Float): Int {
    return when {
        raw >= 138f -> 144
        raw >= 115f -> 120
        raw >= 85f  -> 90
        raw >= 55f  -> 60
        else        -> 60
    }
}
```

## 第三章：能力分级与降级策略

上一章讲了 AGSL 是 SDK 33+ 才有。这一章讲实际怎么处理这件事，以及为什么最后没有做成"自动降级 + 自动恢复"那么理想化的东西。

先看结论表：

| Android 版本 | SDK | 玻璃表现 | 用户感知 |
|---|---|---|---|
| 13 及以上 | 33+ | 实时折射 + 色散 + 动态高光 | 完整液态玻璃 |
| 12 | 31–32 | `RenderEffect` 真模糊 + 半透明 + 高光 | 像磨砂玻璃，边缘没有弯曲 |
| 6 ~ 11 | 23–30 | 半透明 + 渐变 + 描边 | 像磨砂亚克力，能看出层次 |

这里有一个反直觉的地方：**降级不是"越老越蒙"，而是"越老越平"。**

Android 12 那一档还有真模糊，所以背景是糊的，只是边缘不弯。Android 11 及以下连模糊都没有，只能靠半透明底色 + 描边模拟"一层玻璃"，背景还是清晰的，只是透过一层带色的膜看。

这也是为什么坚持把壁纸模糊写在背景层而不是玻璃层：

```kotlin
Box(
    Modifier
        .fillMaxSize()
        .graphicsLayer {
            compositingStrategy = CompositingStrategy.Offscreen  // RenderEffect 需要先离屏
            renderEffect = if (blurRadius > 0f) {
                android.graphics.RenderEffect
                    .createBlurEffect(blurRadius, blurRadius, Shader.TileMode.CLAMP)
                    .asComposeRenderEffect()
            } else null
        }
)
```

壁纸本身是糊的，那么所有玻璃层"透过来的东西"天然就是糊的，低版本系统上即使没有 AGSL，看起来也还是有玻璃感，而不是"一块透明塑料片下面压着一张高清照片"。

`compositingStrategy = CompositingStrategy.Offscreen` 这行也容易被忽略：`RenderEffect` 必须作用在离屏层上，如果不先离屏，模糊会作用到整个窗口，把上面的文字也糊掉。

至于降级逻辑本身，没有写一大堆 `if (Build.VERSION.SDK_INT >= 33)` 去手写两套代码。库自己会探测能力：AGSL 可用就走着色器，不可用就走替代路径。业务层只需要知道一件事：**同一个 `GlassSurface` 调用，在所有版本上都能正常工作，只是效果不一样**。

这是库做得好的一点，但也正是下一章所有性能问题的根源——效果好，是因为它真的在实时算。

## 第四章：性能 —— 我试过但失败的所有方案

这一章是写这篇文章最想写的一章，因为它最真实。

### 4.1 问题是什么

液态玻璃的 AGSL 着色器是**实时计算**的。每一层玻璃 = 一次片元着色器调用，覆盖该玻璃面板的每一个像素。

工具页有 7 张玻璃卡，每张卡里还有 `GlassButton`（按钮密密麻麻，20 多个），外加底部导航和顶栏。滚动的时候，每一帧要跑 **20 多个着色器实例**，每个实例还要遍历自己的像素面积。

结果就是：滚动明显掉帧。

Android Studio 的 Layout Inspector 帮不上忙（这是 GPU 侧的开销，不是布局问题），Profiler 也只是告诉你"GPU 忙"。能确定的是：掉帧跟着玻璃数量走，玻璃越多的页面越卡，工具页最卡。

### 4.2 我试过的所有方案

**❌ 方案一：降低卡片数量**

最直接的想法：7 张卡太多，合并成 4 张。

做了，改完了，效果也确实好。但反馈很明确：**要原来的布局**。合并之后功能分组被打乱了，操作路径变长，一个本来"一眼看到所有按钮"的页面变成了"要点开才看到"。

**回滚。** 这一条记下来是因为它最容易被忽略：性能优化的前提是不改需求。用户没要你合并卡片，你合并了就是改需求。

**❌ 方案二：降采样预烘焙壁纸**

第二个想法：玻璃模糊本质上是"底色模糊"，那我把壁纸提前缩到很小再放大，不就有模糊效果了吗？而且这个操作只做一次，不占实时开销。

听起来很完美。实际做出来：**壁纸变成了一块一块的马赛克色块**。

原因很简单：缩小 96px 再放大，等于用双线性插值去重建一张低分辨率图。真正的 `RenderEffect` 高斯模糊是**逐像素加权卷积**，它保留颜色过渡的连续性；而"缩小-放大"是把信息**扔掉**了再猜回来。前者是模糊，后者是像素化。

这个方案彻底失败。而且失败得很明显——一眼就能看出来这不对，不是"稍微差一点"。

**❌ 方案三：滚动时关闭折射**

第三个想法：滚动的时候把 `lens()` 关掉，只保留 `blur()`，滚动停下来再恢复。

做出来是：**闪烁**。

因为滚动状态是连续的，`isScrollInProgress` 在一帧之内会翻转。折射开→关→开，视觉上就是边缘在"跳"。而且 `lens()` 参数的突变不会走动画，是硬切。

这个方案在原理上就有缺陷：**动态切换材质，本质上就是让材质在变**。

**❌ 方案四：加 `tools:overrideLibrary` 强上 minSdk 21**（这个不算性能方案，但同期踩的）

想支持 Android 5.0（SDK 21），因为有些老展讯机器还停在 5.0。加了 `tools:overrideLibrary` 也没用——`compose.animation.core`、`compose.animation`、`foundation-layout`、`ui-unit` 这四个库的 `minSdk` 硬编码是 23，反复加 override 也过不了编译。

最后只能定 minSdk 23。

### 4.3 当前的处理方式

在"接受掉帧"和"改需求"之间，找到了一个**改动最小、不破坏视觉**的折中：

**第一，工具页改用 `LazyColumn`。**

原来是 `Column + verticalScroll`，所有卡片都在组合树里，即使滚出屏幕外，Compose 仍然会布局和绘制它们（只是被裁剪掉了）。`LazyColumn` 会把离屏的 item 直接移出组合树，理论上能省掉离屏的着色器开销。

```kotlin
val scroll = rememberLazyListState()

LazyColumn(
    state = scroll,
    modifier = Modifier.fillMaxWidth().padding(horizontal = 2.dp),
    verticalArrangement = Arrangement.spacedBy(10.dp)
) {
    item { GlassCard(backdrop) { /* FDL 选择 */ } }
    item { GlassCard(backdrop) { /* PAC 固件 */ } }
    // ……
}
```

**第二，滚动期间只降级按钮的 `lens`，不动卡片的。**

加了一个全局开关：

```kotlin
object CheapGlass {
    // 用 Compose 快照状态而不是普通字段：
    // 滚动的某个瞬间恰好没有按钮重组，普通字段的变化就会被漏掉，
    // 导致滚动结束后廉价模式一直卡在开启/关闭状态。
    private var _enabled by mutableStateOf(false)
    var enabled: Boolean
        get() = _enabled
        set(value) { _enabled = value }
}
```

然后工具页监听滚动状态：

```kotlin
LaunchedEffect(scroll) {
    snapshotFlow { scroll.isScrollInProgress }
        .distinctUntilChanged()
        .collectLatest { scrolling ->
            if (scrolling) {
                CheapGlass.enabled = true
            } else {
                delay(180)               // 停止后再等 180ms，避免惯性滚动结束时抖动
                CheapGlass.enabled = false
            }
        }
}
```

按钮内部据此决定要不要跑 `lens`：

```kotlin
val pressed by interaction.collectIsPressedAsState()
// 高性能模式且未按下时，去掉 lens 与 layerBlock：静止按钮不需要每帧折射
val cheap = CheapGlass.enabled && !pressed

effects = {
    vibrancy()
    blur(2.dp.toPx())
    if (!cheap) {
        lens(12.dp.toPx(), 24.dp.toPx())
    }
}
```

为什么这一条不会像方案三那样闪烁？因为**降的是按钮，不是卡片**。

滚动的整个过程中，卡片（也就是屏幕上面积最大的那些玻璃）始终保持完整折射；变的只有按钮——而按钮的 `lens(12dp, 24dp)` 在这么小的面积上，视觉贡献本来就微乎其微。滚动时用户的眼睛在追卡片，不会去盯按钮的边缘有没有弯。

另外 `cheap` 里还带了 `&& !pressed`：手指按下的瞬间 `cheap` 变 false，`lens` 立刻回来，按下反馈完全保留。

**第三，接受现实。**

说实话，前两条只是"减轻"，不是"解决"。工具页在最烂的机器上滚动还是会掉帧，这是客观事实。

### 4.4 核心结论

这一章想说的话只有一句：

> **这个库的视觉效果和性能是硬绑定的。**

想要 iOS 那种液态玻璃的质感，就必然要付着色器成本。这不是"实现得不好"，而是这条路的物理成本：真折射 = 每个像素按法线偏移采样 = 每个像素都要算。你没法用"更便宜的算法"得到同样的结果——方案二（降采样）和方案三（关折射）已经证明了，便宜的结果就是不一样的结果。

所以站在十字路口只有两条路：

```
        ┌─────────────────────────┐
        │  液态玻璃质感要不要？    │
        └───────────┬─────────────┘
                    │
        ┌───────────┴────────────┐
        ▼                        ▼
   ✅ 要                     ❌ 不要
        │                        │
   接受着色器成本            回到半透明磨砂
        │                        │
   中低端机掉帧              全机型流畅
```

我选左边。原因是我做这个项目的初衷就是"想要那个效果"，如果为了流畅把它砍成磨砂，那重写的意义就没了——老工程本来就有半透明 drawable。

但我也在代码里留了后路：`CheapGlass` 这个开关是全局的，实在受不了的机器可以通过它把所有按钮降级。这个开关的存在本身，就是对上面那个结论的诚实记录。

## 第五章：刷机引擎与 UI 的解耦

UI 讲完了，讲讲另一条线：这个 App 到底是怎么刷机的。

### 5.1 BSDL 协议，简述

展讯的刷机走的是 **BSDL**（Spreadtrum Bootloader Download Protocol）。帧格式是 HDLC 风格的：

```
┌──────┬────────┬────────┬──────────┬────────┐
│ 0x7E │ TYPE   │ LEN    │ PAYLOAD  │ 校验   │
│ 头   │ 1 byte │ 2 byte │ N bytes  │ CRC16  │
└──────┴────────┴────────┴──────────┴────────┘
                 0x7D 是转义字符，数据里出现 0x7E/0x7D 都要转义
```

`BslProtocol.java` 里定义的命令集（摘一部分）：

```java
public static final int CMD_CONNECT       = 0x00;
public static final int CMD_START_DATA    = 0x01;
public static final int CMD_MIDST_DATA    = 0x02;
public static final int CMD_END_DATA      = 0x03;
public static final int CMD_EXEC_DATA     = 0x04;
public static final int CMD_NORMAL_RESET  = 0x05;
public static final int CMD_READ_FLASH    = 0x06;
public static final int CMD_ERASE_FLASH   = 0x0A;
public static final int CMD_REPARTITION   = 0x0B;
public static final int CMD_READ_PARTITION= 0x2D;
public static final int CMD_CHECK_BAUD    = 0x7E;
public static final int CMD_POWER_OFF     = 0x17;
```

### 5.2 FDL 两段式引导

展讯的刷机必须经过两段式引导加载器 **FDL**（Flash Download Loader）：

```
BootROM 阶段（芯片固化在 ROM 里的代码）
   │
   ├─ USB controlTransfer(0x21, 34, 0x601)     ← 建立 BROM 链路
   ├─ CMD_CHECK_BAUD(1) → 期望 REP_VER
   ├─ 解析 VER，判断是否 SPRD3（非 SPRD3 = secureBoot）
   ├─ CMD_CONNECT
   │
   ├─ 发送 FDL1（约 37KB）@ addr1
   │    START_DATA → MIDST_DATA × N → END_DATA
   ├─ CMD_EXEC_DATA → ACK
   │
FDL1 阶段
   ├─ CMD_CHECK_BAUD(4) × 最多 12 次重试 → REP_VER
   ├─ 从 VER 字符串里抠出 CHIP ID（"CHIP ID = 0x..."）
   ├─ CMD_CONNECT
   │
   ├─ 发送 FDL2（约 435KB）@ addr2
   │    （注意：FDL2 阶段不带 CRC16，用 sum checksum）
   ├─ CMD_EXEC_DATA → ACK 或 INCOMPATIBLE_PARTITION(0x96)
   │
FDL2 阶段
   ├─ CMD_READ_PARTITION      读分区表
   ├─ CMD_START/MIDST/END     写分区
   ├─ CMD_READ_FLASH          读分区
   ├─ CMD_REPARTITION         重新分区
   └─ CMD_NORMAL_RESET / POWER_OFF
```

分段发送的核心就一段循环：

```java
private void sendBuf(long saddr, boolean ed, int step, byte[] mem, int size) {
    resetSpeedCounter();
    byte[] data = new byte[8];
    w32be(data, 0, saddr);      // 起始地址
    w32be(data, 4, size);       // 总长度
    encodeMsg(BslProtocol.CMD_START_DATA, data, 8);
    if (!sendAndCheck(5000)) throw new RuntimeException("START_DATA失败");

    for (int i = 0; i < size; ) {
        if (cancelled) throw new RuntimeException("已取消");
        int n = Math.min(size - i, step);
        encodeMsg(BslProtocol.CMD_MIDST_DATA, mem, i, n);
        if (!sendAndCheck(5000)) throw new RuntimeException("MIDST_DATA失败");
        i += n;
        updateSpeed(n);
        progress((int) ((i * 100L) / size), "发送中...");
    }

    if (!ed) return;
    encodeMsg(BslProtocol.CMD_END_DATA, null, 0);
    if (!sendAndCheck(5000)) throw new RuntimeException("END_DATA失败");
}
```

`step` 默认 528，会被夹在 64 ~ 0xF800 之间。528 不是随便选的，它和 USB 传输的边界对齐、也和校验块大小相关。

关于流程，这里要感谢开源项目 **`ilyakurdyukov/spreadtrum_flash`（也就是 `spd_dump`）**——FDL 流程是对着它的实现核对的。其中最关键的一条经验是：

> **只需发送地址，不需要执行地址跳转。**

很多文档里把 "send_file" 和 "exec" 写成两个必需步骤，也有的实现会额外发一个"跳到 exec_addr" 的包。实际上展讯的 FDL 只要把 `EXEC_DATA` 发出去，芯片就会从加载地址开始跑，不需要单独跳转。一开始按"需要跳转"的思路写，卡了很久，对照 `spd_dump` 才发现这一步是多余的。

```json
    "size2": 1062104
  }
]
```

注意 **UMS9230 的地址完全不一样**（`0x65000800` / `0xB4FFFE00`，其他芯片大都是 `0x5000` / `0x9EFFFE00`，SC9863A/UMS512 是 `0x5500`）。这不是配置错，是平台架构不同。地址填错 FDL 就跑不起来，所以芯片选择必须由用户确认，不能自动猜。

用户也可以完全绕过内置 FDL，自己在工具页选 FDL1 / FDL2 并填地址，选好之后"绑定到连接页"，连接页的"一键发送"就会用自定义的那套。

### 5.4 Bridge 模式：UI 与引擎的解耦

这是重写过程中最重要的架构决定。

老工程是一个 113KB 的 `MainActivity`，引擎回调直接在里面改 `TextView`。重写成 Compose 之后，如果把引擎回调直接塞进 Composable，会有三个问题：

1. 引擎回调来自引擎线程，改 Compose 状态必须在主线程；
2. Composable 会因为重组而反复创建回调，导致重复注册；
3. UI 层拿到引擎线程的对象，随时可能踩到并发问题。

所以中间加了一层 **`FlashEngineBridge`**（45KB）。它的职责很明确：

```
┌──────────────────────────────────────────────┐
│  LiquidGlassScreen.kt / GlassButton / …      │
│  （纯 Compose，只读 state）                   │
└──────────────────────┬───────────────────────┘
                       │  vm.progressPct
                       │  vm.logs / vm.connected / vm.partitions
                       ▼
┌──────────────────────────────────────────────┐
│  FlashEngineBridge.kt                         │
│  ┌────────────────────────────────────────┐  │
│  │ var connected by mutableStateOf(false) │  │
│  │ var progressPct by mutableStateOf(0)   │  │
│  │ val logs = mutableStateListOf<String>()│  │
│  │ val partitions = mutableStateListOf<>()│  │
│  └────────────────────────────────────────┘  │
│                                               │
│  private val main = Handler(Looper.getMainLooper())│
│                                               │
│  → 所有引擎回调都 main.post { ... } 后才改状态 │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│  UsbFlashEngine.java（152KB，一行没改）       │
│  BslProtocol.java / UsbPermissionManager.java │
└──────────────────────────────────────────────┘
```

核心就是**线程切换**这四行：

```kotlin
private val callback = object : UsbFlashEngine.Callback {
    override fun onLog(msg: String?) {
        msg?.let { appendLog(it) }
    }

    override fun onProgress(pct: Int, op: String?) {
        main.post {
            progressPct = pct.coerceIn(0, 100)
            progressOp = op ?: ""
        }
    }

    override fun onConnected(ok: Boolean, info: String?) {
        main.post {
            connected = ok
            appendLog(if (ok) "设备已连接: ${info ?: ""}" else "连接失败: ${info ?: ""}")
        }
    }
}
```

**给自己定了一条铁律：引擎逻辑一行都不改。**

`UsbFlashEngine`、`BslProtocol`、`UsbPermissionManager`、`LicenseDecoder/Generator/Manager`、`NativeBinHelper` 全部原样搬过来。Bridge 的唯一职责是"把引擎的 Java 调用翻译成 Compose 能读的状态"，以及把 UI 的点击翻译回引擎调用。

这么做的好处非常实际：**引擎是这套工具最贵、最危险的部分**（刷机刷坏了是硬件损失）。如果在重写 UI 的同时顺手"优化"引擎，一旦出问题就分不清是 UI 还是引擎的锅。

Bridge 里还做了一件事：把命令方法逐字照搬原工程的 `runCmd` / `DsdlActivityImpl`，连 requestCode 都不改：

```kotlin
companion object {
    const val REQ_STORAGE            = 100
    const val REQ_SAVE_LOG           = 200
    const val REQ_SAVE_LOG_AS        = 205
    const val REQ_SELECT_FILE        = 201
    const val REQ_SELECT_FDL         = 202
    const val REQ_SELECT_FDL2        = 208
    const val REQ_SELECT_PAC         = 203
    const val REQ_SELECT_APK         = 204
    const val REQ_SELECT_SAVE_DIR    = 209
    const val REQ_SELECT_BATCH_DIR   = 207
}
```

`MainActivity` 那边就是一个 `when (requestCode)` 的转发：

```kotlin
override fun onActivityResult(requestCode: Int, resultCode: Int, data: Intent?) {
    if (resultCode != RESULT_OK) return
    val uri: Uri = data?.data ?: return
    when (requestCode) {
        FlashEngineBridge.REQ_SELECT_FILE      -> flashVm.onWriteFilePicked(uri)
        FlashEngineBridge.REQ_SELECT_FDL       -> flashVm.onFdlPicked(uri)
        FlashEngineBridge.REQ_SELECT_FDL2      -> flashVm.onFdl2Picked(uri)
        FlashEngineBridge.REQ_SELECT_PAC       -> flashVm.onPacPicked(uri)
        FlashEngineBridge.REQ_SELECT_SAVE_DIR  -> flashVm.onSaveDirPicked(uri)
        FlashEngineBridge.REQ_SAVE_LOG_AS      -> flashVm.onSaveLogPicked(uri)
        FlashEngineBridge.REQ_SELECT_BATCH_DIR -> flashVm.onBatchDirPicked(uri)
    }
}
```

连 SAF 启动器都做成注入的：

```kotlin
// MainActivity 里：
flashVm.safLauncher = { requestCode, intent ->
    startActivityForResult(intent, requestCode)
}
```

这样 Bridge 里发起文件选择不需要持有 Activity 引用，也就不会泄漏。

### 5.5 一个真实的初值顺序坑

Bridge 里有一段注释，是 debug 了一下午才写下的：

```kotlin
// 原工程 selectedChipAddr1/2 —— 必须在 init{} 之前声明，
// 因为 init → loadChips → selectChip / useBuiltinFdl(后台线程) 会写这些委托属性，
// 若声明在 init 之后，后台线程可能先于初始化执行并写入而触发 NPE。
var selectedChipAddr1 by mutableStateOf("0x5000")
    private set
var selectedChipAddr2 by mutableStateOf("0x9EFFFE00")
    private set
```

Kotlin 里 `by mutableStateOf(...)` 是委托属性，委托对象本身在**声明那一行的初始化器**里才创建。如果 `init {}` 里调用的方法在后台线程里访问了这个属性，而此时委托对象还没创建，就是 NPE。

Java 的对象初始化顺序是"字段 → init 块 → 构造体"，Kotlin 也类似，但只要中间蹦出一条后台线程，这个顺序就不可靠了。**结论：凡是会被 init/后台线程写入的状态属性，都必须在 init 之前声明。** 这条教训适用于所有"构造期就启动线程"的类。

### 6.2 坑：Compose 1.12.0 硬性要求 minSdk 23

这个坑前面提过，这里展开说，因为它很有代表性。

想支持 Android 5.0（SDK 21），理由很实际：有些老展讯机器停在 5.0。

第一个想法是按老办法加 `tools:overrideLibrary`：

```xml
<uses-sdk tools:overrideLibrary="androidx.compose.animation.core,
                                 androidx.compose.animation,
                                 androidx.compose.foundation.layout,
                                 androidx.compose.ui.unit" />
```

**没用。** 因为 manifest 的 override 只能绕过 AAPT 的**资源** minSdk 检查，而 Compose 这几个库的 `minSdk` 是写进 **AAR 的字节码和 class 文件版本**里的。就算你骗过了 AAPT，到了 dex 阶段、到了运行期，`java.lang.VerifyError` 还是会找上来。

具体卡住的四个库：

```
androidx.compose.animation.core
androidx.compose.animation
androidx.compose.foundation.layout
androidx.compose.ui.unit
```

它们的 `minSdk` 都是 **23**。

这里还有一个技术原因：Compose 从 1.x 后期开始用了不少 Java 8+ 的语言特性（默认方法、`invoke-dynamic` 优化），这些特性的 desugar 支持在 API 23 以下是有条件的，官方选择了 23 作为安全线。

**结论：minSdk 定 23。** 没有别的办法。Android 5.0 用户只能继续用老版本。

### 6.3 坑：中文路径导致构建失败

这个坑和 Android 无关，但卡了很久。

`aapt2`、`javac`、`gradle` 这三套工具链**全都不支持中文路径**。同样的资源，放在 ASCII 路径下编译成功，放在 `D:\123\测试中文\` 下直接报：

```
failed to open directory
```

而且报错信息指向的是内部临时目录，很难第一时间反应过来是路径问题。

老工程（AIDE 那套）是用 `build_apk.py` 解决的：脚本自动把工程镜像到一个纯 ASCII 的临时目录，编译完再把产物复制回来。

```python
# 大致逻辑
WORK = Path(tempfile.gettempdir()) / "sprd_build_ascii"   # 纯 ASCII
shutil.copytree(SRC_PROJECT, WORK, dirs_exist_ok=True)
# → aapt2 编译资源 → javac → d8 → zipalign → apksigner
# → 复制回原目录
```

Compose 版这边，做了两件事：

1. 工程目录名本身改成 ASCII：`展讯-compose` → 实际构建时镜像到 ASCII 目录
2. **写了一个静态检查脚本 `compose_check.py`**，在构建前跑一遍

第二个东西比第一个重要。因为当构建环境本身不可靠（路径、网络、SDK 版本都可能出问题）时，**你需要一个不依赖构建就能验证代码正确性的手段**。

`compose_check.py` 干三件事：

```python
# 1. 所有 com.kyant.backdrop 的 import 是否真的存在于 2.0.1 源码里
KNOWN = {
    "Backdrop", "LayerBackdrop", "rememberLayerBackdrop", "layerBackdrop",
    "drawBackdrop", "drawPlainBackdrop", "blur", "lens",
    "Highlight", "Shadow", "InnerShadow", "HighlightStyle",
}

# 2. Kotlin 大括号平衡（去注释、去字符串后数）
def check_braces(name, src): ...

# 3. drawBackdrop / lens / blur 的具名参数是否合法
DRAW_BACKDROP_PARAMS = {
    "backdrop", "shape", "effects", "highlight", "shadow", "innerShadow",
    "layerBlock", "exportedBackdrop", "onDrawBehind", "onDrawBackdrop",
    "onDrawSurface", "onDrawFront",
}
LENS_PARAMS = {"refractionHeight", "refractionAmount", "depthEffect", "chromaticAberration"}
BLUR_PARAMS = {"radius", "edgeTreatment"}
```

第 3 项救过一次：`lens()` 的参数名如果写错（比如把 `chromaticAberration` 写成 `chromatic`），Kotlin 编译器会报"找不到具名参数"，但那种报错信息在一堆 Compose 泛型推导错误里极难定位。用脚本先查，5 秒钟出结果。

### 6.4 坑：AIDE 无法编译 Compose

原项目用 AIDE（手机端 IDE）构建，整个工程就是 `app/src/main/java` + `app/src/main/res`，不需要 Gradle。

重写成 Compose 之后，AIDE 直接没戏：

- AIDE 不支持 Compose 编译器插件（`org.jetbrains.kotlin.plugin.compose`）
- AIDE 不支持 Kotlin DSL（`build.gradle.kts`）
- AIDE 无法处理 `io.github.kyant0:backdrop:2.0.1` 这种需要解析传递依赖的 Maven 库

**结论：Compose 版必须在 PC 上构建。** 这是不可逆的取舍——你不可能既享受现代 Compose，又保留手机端编译的便利。

### 6.5 其它小坑

**`getDeviceId()` 冲突。** `ContextWrapper` 在 API 33 新增了一个 `final` 的同名方法，如果你在自定义 View 或 Manager 里也定义 `getDeviceId()`，会编译失败（不能覆盖 final 方法）。改名为 `getLocalDeviceId()` 即可，别改回去。

**SDK 33 的广播注册。** `registerReceiver` 在 API 33+ 要求显式指定导出标志：

```kotlin
if (android.os.Build.VERSION.SDK_INT >= 33) {
    context.registerReceiver(usbReceiver, filter, Context.RECEIVER_NOT_EXPORTED)
} else {
    context.registerReceiver(usbReceiver, filter)
}
```

**API 31 的 PendingIntent 可变性。** USB 权限请求必须用 `FLAG_MUTABLE`，否则系统无法往 Intent 里塞设备信息：

```kotlin
val flags = if (android.os.Build.VERSION.SDK_INT >= 31) PendingIntent.FLAG_MUTABLE else 0
```

**存储权限分档。** Android 11+ 需要 `MANAGE_EXTERNAL_STORAGE` 并跳设置页申请；Android 6~10 走运行时权限。刷机工具要读写任意路径（PAC、固件、分区镜像），所以这个权限没法避免。

## 结语：关于取舍

写到这里，把这个项目最重要的几个决定列一下，因为技术细节会过时，决定背后的理由不会。

**第一，选了 Compose，就失去了 AIDE。**

这不是"要不要现代 UI"的选择题，而是"用不用官方液态玻璃库"的必然结果。官方库从 2.0 起只有 Compose Multiplatform 版本，没有 View 版 API。想要官方效果，就得上 Compose；上 Compose，就必须在 PC 上构建。

顺带说一句：在老工程里其实也写过一版 View 自研的液态玻璃引擎（`LiquidGlassEngine.java` + `LiquidGlassView.java`），AGSL 折射、色散、模糊都复刻了。但它有硬伤——View 版的背景捕获只能"软件绘制窗口到小位图"，滚动时有约 120ms 的延迟刷新；而 Compose 版用的是 `GraphicsLayer`，是真正的 GPU 录制。**这是两代技术的差距，不是努力能补上的。**

**第二，选了实时折射，就接受了掉帧。**

第四章那一整章都在讲这件事。试过合并卡片（用户不要）、试过预烘焙壁纸（变马赛克）、试过滚动关折射（闪烁），最后发现这些方案要么改需求、要么改视觉、要么改手感——**没有一个能在"保持效果"的前提下把性能问题真正解决掉**。

所以最后留下的方案（`LazyColumn` + 滚动期降级按钮 `lens`）是很小的优化，因为它本来就不该是重点。重点在于承认：**这个效果的成本是真实存在的**。

**第三，引擎一行没改。**

UI 可以从 Java + XML 完全推翻重写成 Kotlin + Compose，但 `UsbFlashEngine.java` 那 152KB 一个字符都没动。`FlashEngineBridge` 的定位很明确——它是个翻译层，不是逻辑层。

这个决定让重写过程中省了大量时间：界面出问题就查 UI，刷机出问题就查引擎，两边永远不会互相污染。而且客户端的 UI 怎么重写都不影响刷机正确性——**这一点对一个会被用来处理硬件数据的工具来说，比什么都重要。**

---

**最后一点感想。**

液态玻璃这个效果做出来的那一刻，确实很有成就感。但做了两个月之后，最满意的部分反而都不是那个折射效果——是 `DampedDragAnimation` 里 `dampingRatio = 1.0` 那个过阻尼弹簧，是 Bridge 里那四行 `main.post { }`，是 `compose_check.py` 这个土办法脚本。

好看的东西会让人一眼记住，但让人愿意长期用下去的，是那些不出错的地方。
